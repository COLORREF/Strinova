# Minecraft 第三人称枪战 Mod：游戏版本与模组加载器调研报告

- 调研日期：2026-10-23
- 项目代号：Strinova
- 目标：Minecraft Java Edition 第三人称枪战射击玩法，并视情况加入特殊机制
- 报告性质：技术选型调研，不包含实现代码

## 一、结论摘要（TL;DR）

### 推荐组合

| 项目 | 推荐 | 具体版本 |
|---|---|---|
| 游戏版本 | Minecraft Java Edition | **26.3**（Wilderness Bound，2026-09-15 正式发布） |
| 模组加载器 | **NeoForge** | **26.3.0.95**（稳定版，无 `-beta` 后缀） |
| Java | JDK 25 | Minecraft 26.x 使用 Java 25 |
| 构建工具 | Gradle 9.6.x | NeoForge 侧要求 Gradle 9.1+；Fabric 侧 26.3 推荐 9.6.0 |
| 构建插件 | ModDevGradle 2.0.x | 以官方 MDK 当前版本为准（26.1 时期为 2.0.141 一系） |
| 映射 | 不需要额外映射 | 26.1 起官方代码未混淆，直接使用 Mojang 官方名称 |
| 动画库 | GeckoLib 5.5.7 + Player Animation Library 1.2.x | 两者均已发布 26.3 构建 |
| 第三人称相机 | 自研为主，兼容 Unbound Third Person | Unbound 已支持 26.3；Leawind 目前最高到 26.2 |

**一句话结论：** 26.3 的开发工具链、动画库和枪械参考实现都已到位，没有必要退回旧版本；在 NeoForge 与 Fabric 之间，NeoForge 26.3 在内容/服务端 API 和枪械模组生态上更完整，因此作为首选。Fabric 26.3 是成立的备选，尤其当团队更偏客户端渲染、性能模组或希望更快跟进版本时。

### 明确不推荐

| 方案 | 不推荐原因 |
|---|---|
| **Forge 26.3**（66.1.0） | 仍在维护，但开发重心、第三方库与新模组已明显迁移到 NeoForge；新项目收益低 |
| **Quilt** | QSL/QKL/QFAPI 自 26.1 起退役，Quilt Mappings 停止维护；生态不足以支撑新项目 |
| **1.20.1 / 1.21.1** | 仅在“直接复用 TaCZ 代码或玩法”时考虑；TaCZ 官方仍停在 1.20.1 Forge |
| **26.4 快照** | 快照不是正式版，不适合作为项目基线 |

### 关键风险提示

1. 26.x 的渲染管线仍在快速重构（26.2 实验性 Vulkan、26.3 引入 OIT），自定义渲染代码需要按版本做适配。
2. Minecraft 原版玩家只有一个 AABB 碰撞箱，**爆头判定需要自己实现分部位命中盒**，不能直接依赖原版。
3. 第三人称下“准星指向”和“枪口位置”天然不一致，必须明确采用**相机射线命中 + 枪口曳光弹表现**的方案，否则会出现打不中准星的问题。
4. TaCZ 代码是 GPLv3，素材是 CC BY-NC-ND 4.0；如果参考或复用，需要遵守相应许可证，商用尤其要谨慎。
5. 如果强依赖 Leawind's Third Person，当前应暂时选择 26.2；如果自己做相机，则 26.3 没有阻碍。

## 二、游戏版本现状

### 2.1 版本号规则已经改变

Minecraft Java Edition 从 2026 年起改用“年份.序号”的版本号，例如 `26.1`、`26.2`、`26.3`。这和过去的 `1.21.x` 是同一套游戏，只是命名方式变了。当前时间点：

| 版本 | 状态 | 发布时间 | 说明 |
|---|---|---|---|
| **26.3** | **最新正式版** | 2026-09-15 | Wilderness Bound 更新，当前应作为基线 |
| 26.4 | 快照开发中 | 2026-10 | 已有 Snapshot 4，不是稳定版 |
| 26.2 | 旧正式版 | 2026-06-15 | 部分模组仍停留在此版本 |
| 26.1.2 | 旧正式版（26.1 热修） | 2026-04-09 | 26.x 系列中模组覆盖相对最广的版本之一 |
| 1.21.11 | 1.21 系列最后一个版本 | 2025-12 | 去混淆前的最后一个版本 |
| 1.21.1 | 上一代“长期模组版本” | 2024-08 | NeoForge 生态中模组数量最多的版本之一 |
| 1.20.1 | 更老的模组黄金版本 | 2023-06 | TaCZ 等大量枪械模组仍停留在此 |

> 版本判断：用户要求“优先最新正式版”。26.3 的工具链、文档和关键库均可用，因此**不需要因为“版本太新”而退回 26.1.2 或 1.21.1**。只有在“必须依赖某个尚未更新到 26.3 的模组”（例如 Leawind's Third Person）时，才考虑 26.2。

### 2.2 26.x 对模组开发影响最大的变化

| 变化 | 发生版本 | 对枪战 Mod 的影响 |
|---|---|---|
| **代码去混淆** | 26.1 | 不再需要 Yarn/MCP 等映射；直接使用 Mojang 官方类名和参数名。旧版模组不能直接运行，至少要重新编译 |
| **Java 25** | 26.1 | 开发环境、Gradle 工具链都要升到 JDK 25 |
| **GUI 渲染重构** | 26.1 | `GuiGraphics` 改名为 `GuiGraphicsExtractor`，`Screen#render` → `extractRenderState`；HUD、准星、弹药 UI 需要按新 API 写 |
| **SDL 替代 GLFW** | 26.3 | 输入/按键处理变化；不要硬编码鼠标键值，统一用 `InputConstants` |
| **OIT 透明渲染** | 26.3 | 半透明物体合成方式改变；自定义透明特效、烟雾、玻璃瞄具需要重新验证 |
| **实验性 Vulkan 渲染器** | 26.2 | 渲染后端开始多元化；自定义 RenderPipeline 的兼容性需要持续测试 |
| **数据包/资源包格式** | 26.3 | 数据包 121.0、资源包 97.1；自定义枪械数据、模型、语言文件都要按新格式 |
| **数据组件化** | 26.1–26.3 | 物品属性越来越多地通过 Data Components 表达；弹匣、配件、开火模式适合用组件实现 |
| **网络包安全** | 2026-05 | NeoForge 修复了网络对象分配漏洞；服务端必须对客户端发包做限流与校验 |

### 2.3 为什么选 26.3

- 它是当前**最新正式版**，符合用户优先级。
- NeoForge、Fabric、Forge 均已发布 26.3 构建。
- 动画与相机相关库已有 26.3 支持：GeckoLib 5.5.7、Player Animation Library、Unbound Third Person。
- 已有 26.3 枪械模组作为可行性证据：Strike Arsenal（Counter-Strike Guns）、Just Enough Guns New。
- 26.3 是 5 周前发布的版本，生态仍在追赶；如果项目需要立刻进入大量模组整合包，26.1.2 的兼容面更广，但这不影响“独立开发一个新 Mod”。

## 三、模组加载器现状

### 3.1 四个加载器的定位

| 加载器 | 当前状态 | 26.3 支持 | 开发工具链 | 生态判断 |
|---|---|---|---|---|
| **NeoForge** | Forge 分裂后的主流继承者 | **26.3.0.95 稳定版** | ModDevGradle 2.0.x / NeoGradle 7.1.x，Gradle 9.1+，JDK 25 | 内容模组、整合包、枪械模组的主力；API 完整 |
| **Fabric** | 轻量、更新快、客户端模组多 | **Loader 0.19.5 + Fabric API 0.161.x** | Loom 1.17，Gradle 9.6.0，JDK 25 | 性能模组、客户端 UI/相机、快速跟进版本 |
| **Forge** | 仍在维护，但重心已转移 | **26.3-66.1.0** | ForgeGradle 6.0.x | 老模组多，新模组与库明显减少 |
| **Quilt** | Loader 仍在，但标准库已退役 | 无独立 26.x 标准库 | 基于 Fabric Loader 0.19.x | 不建议作为新项目目标 |

### 3.2 NeoForge

**优势：**

- 26.3 构建已转正（`26.3.0.95`，无 beta 后缀），不是试验性版本。
- 提供较完整的内容模组基础设施：数据组件、Data Attachment、Capability、网络 Payload 注册、配置系统、事件总线。
- 枪械/战斗类模组的参考实现更多：Strike Arsenal、Just Enough Guns、TaCZ 的非官方 NeoForge 移植都选择或支持 NeoForge。
- 模组整合包受众更大。NeoForge 官方在 2025 年回顾中提到，1.21 已成为 NeoForge 模组数量最多的版本（超过 16000 个模组），说明其内容生态体量。
- 动画库支持完整：GeckoLib 5.5.7、Player Animation Library 均有 NeoForge 26.3 构建。

**劣势：**

- API 抽象层更厚，学习成本高于 Fabric；部分文档仍在追赶 26.x。
- 加载器本身比 Fabric 重，对极端轻量客户端不如 Fabric。
- 26.x 版本迭代快，NeoForge 团队自己也提到人力紧张，新版本稳定构建的等待时间可能比 Fabric 长。

### 3.3 Fabric

**优势：**

- 加载器轻、启动快，客户端模组（Sodium、Iris、Mod Menu、相机模组）生态最强。
- 26.3 支持及时：Loader 0.19.5、Loom 1.17、Fabric API 0.161.x。
- Mixin 使用广泛，做相机、玩家模型、输入拦截等客户端改造很直接。
- 文档按 Minecraft 版本组织，26.x 迁移文档较完整；去混淆后不再需要 Yarn，直接使用 Mojang 名称。
- 26.3 已有枪械模组：Strike Arsenal（Fabric）、Just Enough Guns（Fabric）。

**劣势：**

- “开箱即用”的内容 API 比 NeoForge 少：菜单、Capability、配置、网络注册等需要更多手写代码或依赖第三方库。
- 枪械/内容模组的整体数量和整合包受众小于 NeoForge。
- 部分库（如 Leawind's Third Person）虽然支持 Fabric，但 26.3 尚未更新。

### 3.4 Forge

- 26.3-66.1.0 仍在 2026-10-21 更新，技术上可用。
- 但 Forge 的核心开发者和大量模组作者已转向 NeoForge；新库、新教程、新模组优先支持 NeoForge。
- 对“新项目”而言，选 Forge 会让后续找库、找参考实现、找玩家都更困难。
- 若未来需要兼容老 Forge 模组，可以用 Sinytra Connector 之类的方案评估，但不建议作为主加载器。

### 3.5 Quilt

- Quilt Loader 仍在更新（0.30.0 已跟进到 Fabric Loader 0.19.2），但 **QSL、QKL、QFAPI 自 26.1 起正式退役**，Quilt Mappings 也停止维护。
- 官方明确表示未来重点转向 Loader 本身，而不是模组 API。
- 对开发者来说，Quilt 既没有 Fabric 的生态，也没有 NeoForge 的内容 API，作为新项目目标没有收益。
- 如果用户使用 Quilt，通常可以通过其 Fabric 兼容层运行 Fabric 模组，但这不等于“为 Quilt 开发”。

### 4.3 对 TaCZ 的正确预期

TaCZ 是最成熟的参考，但不能直接拿来用在 26.3：

- 官方版本仍是 **1.20.1 Forge**。
- 非官方移植到 1.21.1 已经需要不少代码改动；26.x 又经历了去混淆、Java 25、渲染管线、GUI、输入等变化，移植成本更高。
- 代码是 **GPLv3**：如果复用代码，衍生作品也需要以 GPLv3 发布。
- 素材是 **CC BY-NC-ND 4.0**：禁止演绎、禁止商用；不能直接修改后打包进自己的模组。

**建议：** 把 TaCZ 当作“交互与数值设计参考”，不要把它当作“可直接继承的代码库”。如果确实想复用，需要先确定项目许可证与商业化路线。

## 五、第三人称枪战的技术可行性分析

### 5.1 相机与瞄准

第三人称枪战的核心不是“把视角切到背后”，而是解决以下几个问题：

1. **相机位置**：越肩偏移、相机碰撞、贴墙收缩、开镜时平滑过渡、FOV 变化。
2. **准星与弹道**：准星在屏幕中心，但枪口在角色手上。若从枪口发射，近距离会打不中准星；若从相机发射，子弹看起来又从枪口出。
3. **身体朝向**：原版玩家的头部和身体朝向是分开的（`yHeadRot` / `yBodyRot`），第三人称瞄准时身体需要转向相机方向，移动时又要保持自然。
4. **服务端一致性**：服务端看到的玩家朝向、瞄准方向必须与客户端准星一致，否则会出现“客户端命中、服务端不认”的问题。

**推荐方案：**

- 瞄准时以**相机中心射线**作为命中射线，射线起点用玩家眼睛位置做合法性校验。
- 曳光弹、枪口火光从枪口位置生成，但命中点使用相机射线的结果；近距离做一次“枪口 → 命中点”的视觉收敛。
- 开镜/瞄准时让身体朝向跟随相机 yaw，非瞄准时身体朝向跟随移动方向；通过自定义包同步“瞄准状态”和相机 yaw。
- 服务端用同一套射线参数复算，并校验射线起点、距离、视线遮挡、开火冷却与弹药。

**难度评估：中等偏高。** 有成熟参考（Strike Arsenal、TaCZ + Leawind 兼容补丁、Unbound Third Person），但不是“装个相机模组就完成”。

> **补充：原版 F5 第三人称并不是“不能用”。** 原版确实有第三人称视角（F5 循环：第一人称 → 背后第三人称 → 正面第三人称），也可以在其中持枪、射击。但它是一个“观察视角”，不是为枪战设计的控制方案，主要差距如下：
>
> | 原版第三人称 | 枪战 Mod 需要 |
> |---|---|
> | 相机在头部正后方，角色会挡住视野 | 越肩偏移、左右肩切换 |
> | 准星在屏幕中心，射线却从玩家眼睛/头部发出 | 相机中心射线与准星严格对齐 |
> | 没有开镜/ADS、FOV 过渡、瞄准姿态 | 开镜、FOV/灵敏度、瞄准动画 |
> | 身体/头部朝向与移动绑定，动画只有原版手臂摆动 | 上半身瞄准、下半身移动、全身换弹/切枪动画 |
> | 相机碰撞简单，贴墙会突然拉近 | 相机碰撞、平滑收缩、遮挡处理 |
> | 服务端只知道头部 yaw/pitch | 同步“瞄准状态 + 相机 yaw”并做校验 |
>
> 所以：
> - **做原型**：可以直接用原版 F5 + 一个枪械物品，先验证伤害、弹药、UI，成本最低。
> - **做成真正的第三人称射击**：需要自定义相机逻辑，或者依赖 Leawind/Unbound 这类相机模组；前者可控性更高，后者省事但增加依赖与兼容成本。

### 5.2 命中判定与伤害

- Minecraft 原版玩家/生物使用**单个 AABB**，没有头、胸、四肢的独立命中盒。
- 爆头需要自己实现：可以在服务端用射线与自定义的头部/躯干/四肢包围盒求交，或者用“命中点高度 + 身体朝向”做近似判定。
- 穿墙需要射线连续检测多个方块，并按方块材质/硬度决定穿透层数与伤害衰减。
- 护甲、距离衰减、命中部位倍率、友伤规则都应在服务端计算。

**建议：** 先做“单 AABB + 头部高度区间”的简化爆头，再升级为多命中盒；不要第一版就做复杂布娃娃/部位伤害。

**难度评估：中等。** Strike Arsenal 已经证明在 26.3 可实现爆头、穿墙、护甲。

### 5.3 动画与模型

第三人称枪战对动画的要求远高于第一人称：

- 需要**全身**的待机、行走、奔跑、瞄准、开火、换弹、切枪、受击、死亡姿态。
- 上半身瞄准与下半身移动需要分层混合。
- 不同枪型（手枪、步枪、狙击、霰弹）需要不同的持枪姿态和换弹动作。
- 武器模型需要独立的骨骼动画（枪机、弹匣、拉栓、开镜）。

**可用方案：**

- **Player Animation Library**：给玩家模型加骨骼，做全身动画；支持 Fabric/NeoForge，已发布 26.3 构建。
- **GeckoLib 5.5.7**：做武器/实体模型与动画；支持 26.3。
- 动画制作走 Blockbench + GeckoLib 插件；需要建立统一的动画状态机（idle / walk / run / aim / fire / reload / equip / hurt / death）。

**建模/贴图/动画工具：**

| 工具 | 用途 | 费用 | 上手难度 | 建议 |
|---|---|---|---|---|
| **Blockbench** | Minecraft 模型与关键帧动画；支持 Java Block/Item、Bedrock Entity 等格式 | 免费 | 低–中 | 首选，必学 |
| **GeckoLib 的 Blockbench 插件**（如 GeckoLib Animation Utils） | 导出 `.geo.json` / `.animation.json`，供 GeckoLib 加载 | 免费 | 低–中 | 做可动枪械（枪机、弹匣、拉栓）时必学 |
| **Aseprite** | 像素贴图、逐帧动画 | 付费（约 20 美元） | 低–中 | 推荐；预算有限可用 Krita/GIMP |
| **Krita / GIMP** | 免费贴图绘制 | 免费 | 低–中 | Aseprite 的免费替代 |
| **Blender** | 高模、雕刻、绑定、复杂动画、烘焙 | 免费 | 高 | 只在做非方块风角色/复杂枪械时使用；原版不能直接加载，需要转模或自定义渲染器 |
| **MagicaVoxel** | 体素风格道具/枪械 | 免费 | 低–中 | 可选，适合快速出体素草图 |
| **Substance Painter** | PBR 贴图 | 付费订阅 | 高 | 原版风格用不上；做光影/PBR 管线时再考虑 |
| **Mixamo** | 现成人形动画 | 免费 | 中（需重定向） | 与 Minecraft 玩家骨架不兼容，不建议第一版使用 |

**推荐工作流：**

1. **枪械**：Blockbench 建低模 → Aseprite/Krita 画贴图 → 需要枪机/弹匣/拉栓动画时用 GeckoLib 插件导出 → 放进 Mod 资源目录并注册渲染器。
2. **角色**：先用原版 64×64 皮肤 + PAL 骨骼动画；需要独立角色模型时，用 Blockbench 的 Bedrock Entity 格式建模，再交给 PAL/GeckoLib。
3. **动画**：Blockbench 时间轴做关键帧；玩家动作用 PAL 兼容的 Bedrock 格式，武器动作用 GeckoLib 动画控制器。

**难度评估：高。** 这是第三人称枪战 Mod 最大的工作量来源，建议尽早确定动画规范和状态机，否则后期会返工。建模本身不难，难的是“持枪姿态 + 换弹 + 跑动 + 瞄准”的全身动画衔接。

### 5.4 渲染与特效

26.3 的渲染变化需要重点关注：

- 26.3 用 **OIT（Order-Independent Transparency）** 替代旧的 Improved Transparency；半透明物体（烟雾、玻璃瞄具、能量护盾）的合成方式变了。
- 26.2 引入**实验性 Vulkan 渲染器**；26.3 继续现代化渲染管线。
- 自定义 RenderPipeline、后处理、粒子渲染都要按 26.x 的新 API 写，不能照搬 1.20.1 教程。
- GUI 侧 `GuiGraphicsExtractor` / `extractRenderState` 是新入口。

**建议：**

- 第一版尽量使用原版粒子、原版音效、原版模型渲染，减少自定义 RenderPipeline。
- 枪口火光、曳光弹、弹壳、弹孔优先用粒子/实体实现；烟雾弹、护盾等半透明效果单独做兼容测试。
- 不要第一版就写自定义 Shader；等核心玩法稳定后再加。

**难度评估：中等偏高。** 主要风险是 26.x 渲染 API 变动频繁，需要持续跟进。

### 5.5 网络与服务端权威

推荐架构：

- **客户端**：输入采集、相机、动画、HUD、本地预测（开火音效、枪口火光、后坐力）。
- **服务端**：弹药、冷却、换弹状态、命中判定、伤害、死亡、掉落、技能冷却。
- **网络包**：开火请求（包含相机 yaw/pitch、射击序号、客户端 tick）、换弹请求、瞄准状态、技能请求；服务端回包确认/纠正。
- **反作弊**：限制开火频率、校验弹药与换弹状态、校验视线遮挡、校验射线起点与最大距离、对异常包做限流。

NeoForge 的 `PayloadRegistrar`、Data Attachment、配置系统能减少样板代码；Fabric 则需要自己组织网络与状态同步，但 Fabric API 也提供 Payload 与 Attachment 能力。

**难度评估：中等偏高。** 单机/局域网可以先用“客户端命中 + 服务端复核”的简化方案；多人 PvP 必须做严格的服务端权威。

### 5.6 性能

- 第三人称相机、全身动画、武器模型、粒子特效都会增加客户端开销。
- 20 人以上 PvP 时，服务端射线检测、伤害计算、发包频率是瓶颈。
- 26.3 的性能模组生态已就绪：Sodium 0.9.2、Iris 1.11.7、Lithium 0.26.x 均有 26.3 构建（Fabric/NeoForge）。
- 建议设定粒子预算、开火特效 LOD、远距离玩家动画降频。

**难度评估：中等。** 需要从第一版就做性能预算，而不是最后优化。

## 六、特殊机制可行性（以 Strinova 风格为例）

项目名为 Strinova。如果目标是类似《卡拉彼丘》的“弦化/纸片化 + 角色技能”玩法，以下是技术可行性评估：

| 机制 | 玩法描述 | 技术实现要点 | 难度 | 建议 |
|---|---|---|---|---|
| **弦化 / 纸片化（2D）** | 角色压扁成纸片，改变受击体积，可贴墙、滑翔 | 自定义实体碰撞箱（极薄 AABB）、玩家模型压扁渲染、相机与动画切换、服务端状态机、移动物理、反作弊 | **高** | 作为“签名机制”单独攻关；不要和基础枪战同时做 |
| **贴墙 / 墙面滑行** | 纸片形态吸附墙面、沿墙移动 | 墙面法线检测、重力取消、输入方向重映射、服务端校验 | 高 | 与弦化共用状态机 |
| **滑翔 / 风道** | 纸片形态在空中滑翔 | 垂直速度控制、风区方块/实体、粒子表现 | 中高 | 可与地图设计结合 |
| **角色技能（Agent）** | 每个角色有主动/被动技能、终极技能 | 数据驱动技能定义、冷却/能量、UI、服务端释放校验 | 中 | 用数据包 + 注册表做可扩展设计 |
| **冲刺 / 滑铲** | 快速位移、降低姿态 | 服务端授权冲量、相机抖动、动画 | 中 | 适合作为第一个特殊机制 |
| **击倒 / 复活** | 倒地等待队友救援 | 玩家状态机、爬行姿态、救援进度、UI | 中 | 团队模式需要 |
| **子弹穿透 / 跳弹** | 穿薄墙、金属跳弹 | 多段射线、材质抗性、跳弹角度计算 | 中 | 先做穿透，跳弹后置 |
| **可破坏掩体** | 打烂木板/玻璃/薄墙 | 方块破坏规则、同步、性能 | 高 | 容易破坏地图平衡，谨慎 |
| **击杀回放 / Killcam** | 死亡后回放击杀者视角 | 位置/朝向采样、回放实体、相机 | 高 | 后期功能 |

**建议的 MVP 边界：**

1. 第一版只做“枪械 + 第三人称相机 + 服务端命中 + 基础 HUD”。
2. 第二个里程碑加入**一个**签名机制（推荐冲刺/滑铲，或“弦化-lite”：仅压扁受击体积 + 贴墙，不做完整滑翔）。
3. 角色技能系统在枪械与相机稳定后再做，避免状态机互相纠缠。

## 七、选型评分与推荐

### 7.1 评分表

权重按“本项目是第三人称枪战玩法、需要动画/相机/服务端战斗”的实际情况设定。

| 方案 | 版本新鲜度 20% | 动画/渲染库 20% | 枪战参考生态 15% | 内容/服务端 API 15% | 性能模组兼容 10% | 受众规模 10% | 长期维护 10% | 加权总分 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| **NeoForge 26.3** | 10 | 9 | 8 | 10 | 9 | 7 | 8 | **8.90** |
| **Fabric 26.3** | 10 | 9 | 8 | 7 | 10 | 8 | 9 | **8.75** |
| Forge 26.3 | 10 | 7 | 7 | 6 | 7 | 6 | 5 | 7.15 |
| NeoForge 1.21.1 | 4 | 9 | 10 | 10 | 9 | 8 | 6 | 7.90 |
| Forge 1.20.1（TaCZ 路线） | 2 | 7 | 10 | 7 | 7 | 6 | 4 | 6.05 |
| Quilt 26.3 | 5 | 6 | 2 | 4 | 8 | 2 | 4 | 4.50 |

> 说明：分数是相对比较，不是绝对质量评价。Fabric 与 NeoForge 的差距很小，最终可以结合团队技术栈决定；如果团队已经熟悉 Fabric，直接选 Fabric 26.3 也完全成立。

### 7.2 最终推荐

**首选：NeoForge 26.3.0.95 + Minecraft 26.3 + JDK 25。**

理由：

1. 26.3 是当前最新正式版，工具链完整，没有“版本太新无法开发”的问题。
2. NeoForge 26.3 构建已转正，内容/服务端 API 更适合枪械、弹药、配件、技能、游戏模式等大量内容。
3. 枪械与第三人称参考实现（Strike Arsenal、JEG、TaCZ 移植）都集中在 NeoForge/Forge 一侧，找参考、找测试玩家更容易。
4. GeckoLib 与 PAL 都有 26.3 NeoForge 构建，动画路线可行。
5. 未来如果要做整合包或服务器，NeoForge 的受众更大。

**备选：Fabric 26.3。**

适合以下情况：

- 团队更熟悉 Fabric / Mixin，或已有 Fabric 客户端模组经验。
- 项目以客户端体验为主，强调 Sodium/Iris 性能与相机手感。
- 希望最快跟进每个 Minecraft drop。
- 不打算做大型整合包，而是做独立玩法模组或 PvP 客户端向模组。

**不建议：Forge 26.3、Quilt、1.20.1/1.21.1。**

除非出现以下例外：

- 必须复用 TaCZ 的现成代码/素材 → 只能先走 1.20.1 Forge，或承担高成本移植。
- 必须兼容某个只在 1.21.1 的模组 → 选 1.21.1 NeoForge，但这是“兼容性优先”而不是“技术最优”。

## 八、建议的实施路线（不含代码）

### M0：工程与规范

- 用 NeoForge 26.3.0.95 + ModDevGradle 2.0.x 建立工程，JDK 25、Gradle 9.6.x。
- 确定包名、Mod ID、许可证、版本号规范。
- 建立 Blockbench/GeckoLib 资源规范：武器模型、动画命名、材质尺寸。
- 建立客户端/服务端代码分离规则（`client` 包只放渲染与输入）。

### M1：最小可玩闭环

- 一把手枪：右键开镜、左键射击、R 换弹。
- 第三人称越肩相机：碰撞、开镜过渡、准星。
- 相机射线命中 + 服务端复算 + 基础伤害。
- 弹药 HUD、命中反馈、枪口火光、简单音效。

### M2：枪械系统

- 自动武器、射速、后坐力、扩散、距离衰减。
- 弹匣/备弹、换弹状态机、切枪。
- 爆头判定（先高度区间，后多命中盒）。
- 护甲、穿透、命中部位倍率。

### M3：第三人称表现

- PAL 全身动画：待机/行走/奔跑/瞄准/开火/换弹/受击。
- GeckoLib 武器动画：枪机、弹匣、拉栓、开镜。
- 上半身/下半身动画分层。
- 第一人称与第三人称模型分离（如果需要）。

### M4：特殊机制

- 推荐先做冲刺/滑铲，验证“移动 + 相机 + 动画 + 服务端校验”的完整链路。
- 再评估弦化/纸片化：碰撞箱、贴墙、滑翔、模型压扁、相机。
- 角色技能系统最后做，避免过早复杂化。

### M5：多人规则

- 团队死斗/炸弹模式等游戏规则。
- 出生点、计分、重生、观战。
- 反作弊与性能压测（20+ 玩家）。

## 九、风险与规避

| 风险 | 影响 | 规避 |
|---|---|---|
| 26.x 渲染 API 频繁变化 | 自定义渲染代码每个 drop 都要改 | 抽象渲染层；第一版尽量用原版粒子/模型；锁定 26.3 并记录升级清单 |
| OIT / Vulkan 兼容性 | 烟雾、护盾、瞄具半透明效果异常 | 单独做透明效果测试；避免依赖旧 Improved Transparency 行为 |
| 动画库滞后 | 26.3 上 PAL/GeckoLib 出问题 | 锁定已验证版本；必要时回退 26.2 或自己写轻量动画层 |
| Leawind 未更新 26.3 | 无法直接依赖最佳相机模组 | 自研相机；把 Leawind 作为兼容目标而不是依赖 |
| 第三人称准星偏移 | 玩家感觉“打不中” | 相机射线命中 + 枪口曳光；服务端同参数复算；参考 TaCZ 兼容补丁的修法 |
| 爆头判定不自然 | 手感差、争议大 | 先做高度区间，再做多命中盒；用可视化调试 |
| 服务端被作弊 | 多人模式崩坏 | 服务端权威；限流；校验冷却/弹药/视线；不要信任客户端命中结果 |
| TaCZ 许可证 | 法律风险 | 代码 GPLv3、素材 CC BY-NC-ND；只参考设计，或遵守许可证 |
| Java 25 / Gradle 9 工具链 | 新手环境配置困难 | 使用官方 MDK/Mod Generator；固定 JDK 与 Gradle wrapper |
| 性能 | 多人卡顿 | 粒子预算、动画 LOD、网络包合并、性能模组测试 |

## 十、待确认问题

在进入实现前，建议确认以下问题；它们会改变选型细节：

1. **玩法定位**：PvP 对抗、PvE 射击、还是单人/小队合作？PvP 对服务端权威和反作弊要求最高。
2. **玩家规模**：预计同服多少人？20 人以上需要更严格的网络与性能设计。
3. **是否必须支持多人联机**：如果只做单机/局域网，第一版可以大幅简化网络层。
4. **是否要做整合包**：要做整合包，NeoForge 更合适；只做独立模组，Fabric 也完全可以。
5. **美术来源**：原创、外包、还是参考 TaCZ？这直接决定许可证与工作量。
6. **是否复刻 Strinova 的弦化机制**：如果“弦化”是核心卖点，需要单独做技术预研；如果只是“特殊机制之一”，建议先做冲刺/滑铲。
7. **是否需要多加载器**：如果未来要同时支持 Fabric 与 NeoForge，建议一开始就用多层工程结构（common + loader 模块），否则后拆成本高。
8. **目标受众版本**：如果玩家群体仍在 1.21.1 整合包，26.3 的受众可能偏小；这属于发行策略，不影响技术可行性。
